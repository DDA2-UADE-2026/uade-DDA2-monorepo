# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This file covers `client/`, the frontend of the monorepo (Vite + React 19 + TypeScript). See the repo root [README.md](../README.md) for the overall project.

## Commands

Run from `client/`:

- `npm run dev` — start the Vite dev server
- `npm run build` — typecheck (`tsc -b`) then production build
- `npm run lint` — ESLint (flat config)
- `npm run preview` — preview the production build
- `npm run gen:api` — regenerate `src/generated/**` from the live OpenAPI spec (see API codegen below)

There is no test runner configured in this package.

## Stack

React 19 + TypeScript, Vite, TanStack Router (file-based) + TanStack Query + TanStack Form, Tailwind CSS v4, shadcn/ui (Base UI primitives, not Radix), Tabler icons, Zod v4, `@hey-api/openapi-ts` for API codegen (client, SDK, types, Zod schemas, React Query options), MapLibre GL / react-map-gl, Recharts, `ogl` (WebGL background effects), `sonner` for toasts.

## API codegen (`@hey-api/openapi-ts`)

`openapi-ts.config.ts` fetches the live OpenAPI spec from `https://api-muni-uade-dev.fabriziob.com/api-docs` and writes to `src/generated/`. Running `npm run gen:api` requires network access to that dev server and **overwrites everything under `src/generated/`** — never hand-edit those files (the directory is also excluded from ESLint).

Generated output, per plugin:
- `client.gen.ts` / `core/` — the fetch client. Runtime config (base URL) is injected via `src/lib/hey-api.ts`, referenced from `openapi-ts.config.ts` as `runtimeConfigPath`. Base URL comes from `VITE_SERVER_URL` (falls back to `http://localhost:8080`).
- `sdk.gen.ts` — plain async functions per endpoint (`@hey-api/sdk` plugin).
- `types.gen.ts` — request/response TypeScript types.
- `zod.gen.ts` — Zod schemas per DTO (`z…` prefixed, e.g. `zLoginRequest`, `zUserManagementResponse`), generated from the same OpenAPI schema constraints (min/max length, `z.email()`, int64 fields as `z.coerce.bigint()`, etc).
- `@tanstack/react-query.gen.ts` — `*Options` (queries) and `*Mutation` builders per endpoint, e.g. `findByIdOptions(options)`, `deleteMutation(options)`, plus query-key helpers. These wrap the SDK functions with `queryOptions`/`UseMutationOptions`.
- `index.ts` re-exports the SDK functions and types (not the Zod schemas or the React Query helpers — import those directly from `@/generated/zod.gen` / `@/generated/@tanstack/react-query.gen`).

Usage pattern (see `src/hooks/use-backend-health.ts`): import the `*Options` helper from `@/generated/@tanstack/react-query.gen` and spread it into `useQuery`/`useMutation` rather than calling the SDK function directly.

The spec currently generated is small (auth/user/role-management endpoints only: `login`, `me`, `health`, `info`, `links`, plus CRUD-ish `create*/update*/delete*/findAll*/findById*`). Most `routes/_app/gestion/**` and `routes/_app/portal/**` pages are UI scaffolding ahead of backend coverage — check `src/generated/types.gen.ts`/`sdk.gen.ts` for what's actually available before assuming an endpoint exists, and don't assume a page's data is wired to a real query. Some code deliberately hand-rolls a Zod schema as a stand-in for a generated one (e.g. `src/components/profile/schemas.ts` says "swap for the schema exported by the generated API client... once /profile is wired up") — when the matching endpoint exists in `zod.gen.ts`, prefer replacing hand-written duplicates rather than adding new ones.

## Routing (TanStack Router)

File-based routes live in `src/routes/`; `src/routeTree.gen.ts` is generated by the `@tanstack/router-plugin` Vite plugin on dev/build (also excluded from ESLint — don't hand-edit).

Layout/route-group structure:
- `routes/__root.tsx` — root shell: loading bar, command palette (`AppCommandShortcut`, lazy), `Toaster`, devtools. Root-level `errorComponent`.
- `routes/_auth/` — unauthenticated flow: `login`, `register`, `callback`, `seleccionar-rol` (role picker for multi-role accounts). Split-screen layout with a lazy map/visual panel shown only ≥768px.
- `routes/_app/` — authenticated shell, split into two independent sections with their own sidebar + layout:
  - `_app/gestion/` — internal municipal management/back-office (auditoría, beneficios, campañas, casos, centros, indicadores, intervenciones, programas, turnos, visitas…), sidebar via `GestionSidebar`.
  - `_app/portal/` — citizen-facing portal (beneficios, campañas, programas, solicitudes, turnos…), sidebar via `PortalSidebar`.
- Errors are handled at two levels: the root route's `errorComponent` (`RouteErrorPage`), and a `CatchBoundary` wrapping just the `<Outlet/>` inside each `_app/*` layout (`SectionErrorFallback`) so a crash in one page doesn't take down that section's sidebar.

The router is created in `src/main.tsx` with `context: { queryClient }` — loaders/route contexts can access the shared `QueryClient` through TanStack Router's typed router context.

There is currently no auth context/provider in `src/context` or `src/providers` (only `theme-context`/`theme-provider` exist) — role selection (`RoleSwitcher`) and role lists are hard-coded placeholders, not driven by real session data yet.

## UI components (shadcn/ui)

`components.json`: style `base-maia`, base color `zinc`, icon library **Tabler** (`@tabler/icons-react`, not lucide), CSS variables enabled, no Tailwind prefix. Aliases: `@/components`, `@/components/ui`, `@/lib`, `@/lib/utils`, `@/hooks` (matches the `@/*` → `src/*` path alias in `tsconfig.app.json`/`vite.config.ts`). Add new primitives with the `shadcn` CLI so they land in `src/components/ui/` respecting this config, rather than hand-writing them.

Important: this project's shadcn components are built on **Base UI** (`@base-ui/react`), not Radix. The polymorphic-render convention is different from stock shadcn docs/most training data:
- Use the `render` prop (e.g. `<Button render={<Link to="/login" />}>`), **not** `asChild`.
- `Button` also takes `nativeButton` (defaults to `!render`).

`cn()` (`src/lib/utils.ts`, `clsx` + `tailwind-merge`) is the standard className-merge helper used throughout.

## Styling / theming

Tailwind CSS v4 (CSS-first, no `tailwind.config.js` — see `@import "tailwindcss"` in `src/index.css`), plus `tw-animate-css`, `shadcn/tailwind.css`, and self-hosted variable fonts via `@fontsource-variable/*` (Inter, Noto Sans, Figtree, JetBrains Mono). Theme tokens are CSS custom properties in OKLCH, defined for `:root` and overridden under `.dark`; `dark:` variant is wired via `@custom-variant dark (&:is(.dark *))`.

Light/dark/system theme state is a custom implementation (`src/providers/theme-provider.tsx` + `src/context/theme-context.ts`, consumed via `useTheme` in `src/hooks/use-theme.ts`) that toggles the `dark` class on `<html>` and persists to `localStorage`; it is **not** `next-themes` even though that package is a dependency (check current usage before assuming it's active).

## Forms

`@tanstack/react-form` (+ `@tanstack/react-form-devtools`) for form state, validated with Zod schemas — prefer schemas from `src/generated/zod.gen.ts` when a matching DTO exists (see codegen note above) instead of duplicating validation by hand.

## Build/tooling notes

- React Compiler is enabled via Babel (`@rolldown/plugin-babel` + `reactCompilerPreset`) in `vite.config.ts` — it affects dev/build performance but generally means manual `useMemo`/`useCallback` are unnecessary for typical component code.
- `vite-plugin-qrcode` prints a LAN QR code in dev (filtered to `192.168.0.*`).
- `rollup-plugin-visualizer` writes a bundle treemap to `dist/bundle-report.html` and auto-opens it on every build.
- Env vars: `VITE_SERVER_URL` (backend base URL, used by the generated API client) and `VITE_CLIENT_URL`. See `.env.example`.
- Production is a static build served by nginx in a container (`Dockerfile`/`nginx.conf`), with SPA fallback (`try_files … /index.html`) — deep links must work without server-side route awareness.
